# Accuracy & refusal

This document states what OrgStandardsBot's accuracy work actually guarantees,
how each guarantee is verified, and — importantly — what is **not** yet proven.

It exists because the previous published numbers could not be substantiated:
the retrieval gold labels were generated by the same local model the bot runs
on, and the LLM judge graded that same model's answers. Those figures measured
self-agreement, not correctness.

## The governing principle

For a compliance product the worst outcome is not "I don't know". It is a
confident, fluent, wrong rule. A refusal costs a user one question; an invented
exemption can cost a certifier their credibility and create liability.

So the system is tuned to **refuse rather than fabricate**, and correctness is
enforced by the system rather than trusted to the model.

## Guarantee 1 — every citation and quantity is traceable to the excerpts

**What it does.** After the reader generates an answer, the pipeline
deterministically extracts every clause/section number it cites and every
quantity-with-unit it asserts (distances, areas, periods, rates), then checks
that each is present in the retrieved excerpts the model was shown. If anything
is untraceable, the answer is regenerated once with a stricter prompt; if it
still fails, the user gets an explicit refusal instead of the answer.

**Where it lives.** `backend/app/rag/citations.py`, enforced in
`RAGPipeline._generate_verified` (`backend/app/rag/pipeline.py`), exposed on the
API as `verified`, `unsupported_citations` and `refusal_reason`.

**Why it was needed.** In live testing the reader answered *"Buffer zones must
be at least 5 metres… and if a farm is under 4 hectares you may waive that
requirement."* The 5-metre figure was right but the clause number was wrong, and
the 4-hectare waiver appears in no document. The answer was fluent and
confident.

**How it is verified.** `backend/tests/test_citations.py` (24 tests) covers
fabricated clause numbers, fabricated quantities, prefix collisions (`3.3` must
not match inside `3.3.2`), per-chunk provenance, and the metric functions.
`backend/tests/test_pipeline.py` covers the end-to-end refusal path, including
that a fabricated answer is retried exactly once and then replaced by a refusal
rather than returned.

**Metrics available today** (model-independent, so reportable honestly):
`citation_precision()` and `fabrication_rate()` in `citations.py`.

**Stated limitation.** This verifies *presence*, not *attribution*. If a model
cites a clause number that genuinely appears in the retrieved excerpts but
belongs to a different rule, the presence check cannot detect it. That case
requires semantic judgement and is routed to the judge/human review loop — it is
explicitly documented in a test
(`test_wrong_but_existing_clause_is_a_known_limitation`) rather than silently
claimed as covered.

## Guarantee 2 — a chunk always carries the clause number it belongs to

**What it does.** Ingestion chunks documents along their own structure: it
detects section headings and numbered clauses, never splits a clause, and
prefixes each chunk with its section context, e.g.

```
[3.3 WINDBREAKS / BUFFER ZONES]
3.3.2 Requirements for buffer zones shall be based on appropriate and
practical situations and in each case will be no less than 5 metres.
```

**Where it lives.** `backend/app/data/chunker.py`, wired into
`DocumentLoader.chunk_pages_structurally` (`backend/app/data/loader.py`).

**Why it was needed.** The original loader cut text on a fixed 512-character
window broken at the nearest period. On NASAA page 26 this captured the tail of
section 3.2 (GMOs) and never included the heading for section 3.3 (buffer
zones), so the reader had **no clause number available in its context** and
guessed one. The root cause was ingestion, not model capability — which means a
larger hosted model would have failed the same way.

**How it is verified.** `backend/tests/test_chunker.py` (11 tests), including a
regression test built from the real page layout asserting that any chunk
containing clause 3.3.2 carries section `3.3` and never claims to be `3.2`.
Confirmed against the real PDF: clause 3.3.2 now lands in a chunk with
`section_number='3.3'`.

## Guarantee 3 — rare terms are not smoothed away by the embedding

**What it does.** Retrieval fuses dense vector search with BM25 lexical search
using Reciprocal Rank Fusion (`backend/app/rag/hybrid.py`). A dense embedding
averages a question into a single vector, which loses the specific tokens that
make a compliance question answerable; lexical search is poor at paraphrase but
excellent on rare exact terms.

**Evidence.** "Can sulphur be used as a fungicide in organic production?" and
the other known misses were checked against the re-ingested AU collection. On
the query *"How many kg of urea can I use?"* dense retrieval returned **no chunk
containing "urea"** in the top 3 while hybrid retrieval returned the clause that
does (`NASAA 7.2.2 Prohibited feeds include urea`). Clause-number lookup is also
rescued: `3.3.2` now surfaces the buffer-zone clause at `p26` ahead of the
back-of-document index page.

**Why RRF rather than score averaging.** Cosine similarity and BM25 scores are
not comparable scales, so any weighted sum requires a normalisation choice that
silently biases one signal. RRF uses only the rankings, so neither signal's
score distribution can skew the result.

**Additional fix.** Back-of-document index pages are dense with clause numbers
and page references, so they win any query containing a clause number while
answering nothing. Demoting them in the lexical ranking alone was not enough —
they also rank well densely — so the fused order is re-sorted to push index-like
chunks to the end. Retrieval must never return an index page as the context for
an answer. They are demoted rather than deleted, so the corpus stays faithful to
the source.

Measured effect on the re-ingested AU collection:

| Query | Dense-only rank 1 | Hybrid rank 1 |
|---|---|---|
| `3.3.2` | NASAA p119 index page | **3.3.1 buffer zones, p26** |
| "What are the buffer zone requirements…" | mixed | **3.3.1 p26** |
| "How many kg of urea can I use?" | no chunk containing "urea" in top 3 | **7.2.2 "Prohibited feeds include urea", p60** |

Config: `HYBRID_RETRIEVAL` (default `true`), `HYBRID_POOL` (default `20`).
Setting `HYBRID_RETRIEVAL=false` restores dense-only behaviour.

**Not yet measured:** the end-to-end effect on the benchmark. These are targeted
per-query checks, not a recall figure over a human-verified set.

## Guarantee 4 — compliance answers are verified before they are shown

Streaming is a presentation detail, not a licence to emit unverified rules. The
`/api/query/stream` path generates and verifies the full answer, then emits a
`verification` event and streams the already-verified text. A 1B-class model
cannot be trusted to police its own citations mid-stream, and a correction event
after the fact would be both confusing and unreliable.

**Trade-off, stated plainly:** this increases time-to-first-token on compliance
questions. On CPU-only hardware end-to-end latency is already the dominating
usability problem (see below).

## What is NOT yet proven

- **No human has verified a benchmark item yet.** The harness exists and the
  drafts are built (110 for AU, including 10 adversarial items), but a machine
  cannot verify its own ground truth — that is the whole point of the design.
  Until a person runs `make bench-review`, there is still no accuracy number,
  and `make bench-score` deliberately refuses to produce one.
- **Retrieval gold labels are page-level, not clause-level**, which inflates
  recall.
- **No paired fine-tune-vs-base measurement** exists, so there is currently no
  evidence the fine-tuned reader outperforms the base model. The fine-tune's
  purpose is output-format and refusal discipline, not knowledge.
- **Latency is not production-grade.** Measured on 16 CPU cores with no GPU:
  16 s for a conversational reply, ~57–77 s for compliance questions, and up to
  99 s in earlier runs. The model has a 4096-token context window.
- **The `redistribute` licensing flags are honoured at the API layer** (full
  copies return 403 where a source forbids redistribution), but the derived QA
  dataset still embeds verbatim standards text; `dataset/strip_context.py` must
  be run before any dataset publication.

## Self-assessment baseline (regression only)

Recorded for comparability over time. **Not** evidence of real-world accuracy —
see the caveats at the top of `evals/README.md`.

| Metric | Value | Caveat |
|---|---|---|
| AU recall@5 | 95.7% | page-level gold labels, model-generated |
| AU gate accuracy | 95% | model-labelled |
| Judge grounded | 82.5% | judge = answer model |
| Judge citation | 82% | measures citation *presence*, not correctness |
| Judge correct | 85.5% | judge = answer model |
| Judge refusal_ok | 12/100 | judge = answer model |

## Observed before/after on the original failure

Measured live against the re-ingested AU collection (local MiniCPM5-1B via
Ollama, CPU-only). These are single observations on the two questions that
originally failed, not a benchmark.

| | Before | After |
|---|---|---|
| Buffer-zone question | cited **"Section 3.2.9"** (a GMO clause) and invented *"if a farm is under 4 hectares you may waive that requirement"* | cites **3.3.1**, the clause that actually carries the 5-metre rule; *no fabricated exemption*; `verified: true`, `unsupported_citations: []` |
| Conversion period | cited **ACO p.108** (an IFOAM annex) for an annual-crop rule | cites **NASAA 7.29**, and the retrieved chunk genuinely contains "one year" and "life cycle"; `verified: true` |
| Top retrieved chunk | `section_number` unpopulated, page-level only | `nasaa sec=3.3.1 clauses=3.3.1,3.3.2,3.3.3 p26 score=0.558` |

The mechanism is visible in the retrieval metadata: the fix is that the clause
number is now *in the excerpt*, so the reader has something real to cite and
the verifier has something real to check.

**Still imperfect and worth stating:** on the conversion question the model
cited NASAA 7.29 when the National Standard §1.2.3 is the more directly
applicable Australian rule (both were retrieved; 7.29 ranked higher). The
answer is grounded and verifiable, but the *best* citation was not always
chosen. That is the attribution problem this layer cannot solve
deterministically.

Note for operators: the model dimension guard rebuilds a collection whose stored
embedding dimension differs from the active model, so switching
`EMBEDDING_FAMILY` requires a re-ingest — the ingest output says so explicitly.
A running backend holds the Chroma store open and will block an ingest; stop it
first.

## The path to a claimable number

The harness for step 1 is built. What remains is the human review itself:

1. **Verify benchmark items** — `make bench-review COUNTRY=au`. Drafts are in
   `evals/bench/bench_au.jsonl`: 100 derived from the question bank plus 10
   adversarial items built to provoke fabrication (the first is the exact
   "farm under 4 hectares" failure). Each verified item needs a reference
   answer and the clause numbers it must cite; the reviewer's name is stamped
   on it.
2. **Score** — `make bench-score COUNTRY=au`. Reports fabrication rate,
   citation attribution, refusal behaviour and verdict accuracy, each with a
   Wilson 95% interval. `--judge` adds semantic correctness and requires a
   judge model different from the reader.
3. **Set the release gate** at **fabrication_rate = 0** and a stated minimum
   correct-answer rate, and publish the exact command that reproduces it.

Until step 1 is done, no accuracy claim should be made publicly — including in
the README or a sales conversation. The scorer enforces this technically: with
zero verified items it reports `no_verified_items` and no metrics at all.
