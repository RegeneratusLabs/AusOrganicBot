# Evaluation harness

Answer reliability is the product. Four tools grade the system end-to-end,
using the 100-question synthetic bank from `scripts/stress_test.py` and
the same LLM configured in `backend/.env`.

## Pipeline

```bash
python3 evals/run_all.py --country au            # one-shot: all four steps
python3 evals/run_all.py --country au --limit 30 # judge subset only
```

Individual steps (all resumable / re-runnable):

| Step | Tool | What it measures |
|---|---|---|
| 1 | `build_eval_set.py` | LLM-annotated gold labels: which retrieved chunks answer each question, and whether the question is answerable at all (**silver labels — generated by the same local model the bot runs on, not by a human**) |
| 2 | `sweep_threshold.py` | Best relevance-gate threshold by gate F1 vs the gold set |
| 3 | `eval_retrieval.py` | recall@5, gate accuracy, per-category breakdown |
| 4 | `llm_judge.py` | End-to-end answer grades: grounded (0-2), citation (0/1), correct (0-2), refusal_ok — with an HTML report for human review |

## Read this before quoting any number below

Two independences are missing from this harness, and both inflate confidence:

1. **The gold labels are model-generated.** `build_eval_set.py` asks the same
   local reader model which chunks are relevant, so `recall@5` measures
   agreement between the model and itself, not retrieval correctness.
2. **The judge grades its own answers.** `llm_judge.py` instantiates
   `LLMClient()` from the same `backend/.env`, so with the default local
   configuration the answer model and the judge are the same model.

These numbers are therefore useful as a *regression baseline* — comparable to
themselves over time — and are not evidence of real-world accuracy. A
human-adjudicated benchmark is the outstanding requirement before any accuracy
claim is made public.

Also note: gold chunks are page-level, not clause-level (`common.py`'s
`chunk_signature` drops the chunk index), so "recall@5" here means "a chunk
from the right page was retrieved".

## Baseline results (all 5 countries, Aug 2026)

Retrieval (recall@5 / gate accuracy; AU at threshold 0.40, others 0.50):

| Country | Answerable | recall@5 | Gate acc |
|---|---|---|---|
| AU | 93/100 | 95.7% | 95% |
| US | 77/100 | 98.7% | 76% |
| NZ | 24/100 | 95.8% | 63% |
| EU | 76/100 | 96.1% | 82% |
| UK | 78/100 | 93.6% | 85% |

(AU was earlier reported as 100%/96%; the freshest artifact,
`evals/data/report_retrieval_au.json`, records 0.957/0.95.)

"Answerable" varies by country — NZ's two documents (framework Act +
Regulations) genuinely cover fewer of the AU-centric probe questions, so
refusals there are the *correct* behavior, which is why gate accuracy
differs rather than retrieval failing.

Answer quality (LLM judge, AU, 100 questions, judge model = answer model):
**grounded 82.5% · citation 82% · correct 85.5% · refusal_ok 12/100**. The
flagged rows are dominated by false refusals where sources were retrieved but
the model judged them not-covered. Treat as a regression baseline only.

Threshold sweep: 0.40–0.45 marginally improves gate F1 (0.989 vs 0.978)
but risks routing casual questions into the RAG path — 0.40 is the current
default (`RELEVANCE_THRESHOLD` in `backend/app/config.py`).

Known retrieval gap (reproduced by the harness): "vermicompost" —
genuinely in the standards but missed at top-5 (chunking/coverage issue).

## Verification layer (independent of the judge)

Deterministic citation verification (`backend/app/rag/citations.py`,
`backend/tests/test_citations.py`) is the one accuracy signal in this repo that
does not depend on a model: after generation it checks that every clause number
and quantity in the answer appears in the retrieved excerpts, and the pipeline
retries strictly once and then refuses if not. Its metrics —
`citation_precision()` and `fabrication_rate()` — can be reported honestly today
and are the numbers the release gate is set on.

## Review workflow

The judge flags low-scoring rows. The intended loop:

1. Run `llm_judge.py` → open `evals/data/report_judge_<cc>.html`
2. Human spot-checks flagged rows (red-highlighted)
3. Fix prompts / chunking / threshold; re-run — the same gold set keeps
   results comparable over time

## Publishing

`evals/data/gold_<cc>.jsonl` is structured for the Hugging Face Hub
(CC-BY-4.0): question + category + answerable + gold chunk references —
no copyrighted text is included. See `dataset/dataset_card.md` for the
publishing checklist.
